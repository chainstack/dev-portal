---
title: "Optimized submission"
description: Enable optimized submission on your Chainstack Arbitrum, Base, Arc, and Robinhood Chain nodes to route transactions through a private, optimized path for faster inclusion.
---

Optimized submission is a Marketplace [add-on](/docs/add-ons) you manage from your node's **Add-ons** tab. It routes your transactions through a private, optimized path designed to reduce inclusion delays. It applies to L2 sequencer chains, where transactions are not broadcast to a public mempool.

It is available on these networks and node types:

| Network | Node types |
| --- | --- |
| Arbitrum Mainnet | [Global Nodes](/docs/global-elastic-node), [Trader Nodes](/docs/trader-node) |
| Base Mainnet | Global Nodes, Trader Nodes |
| Arc Mainnet | Global Nodes |
| Robinhood Chain Mainnet | Global Nodes |

On Global Nodes, optimized submission is available on every plan, including the Developer plan.

On Ethereum and BNB Smart Chain, which have a public mempool where front-running is possible, use [MEV protection](/docs/mev-protection) instead.

### How it works

1. You construct and sign your transaction as usual and send it through your Chainstack endpoint as `eth_sendRawTransaction`.
2. Instead of the default node route, it is routed through a private, optimized submission path.
3. Once included in a block, it appears on-chain as normal, and you can retrieve it with the regular methods such as [eth_getTransactionByHash](/reference/arbitrum-gettransactionbyhash).

### What happens if private routing fails

If the optimized submission path fails, Chainstack sends the transaction through the node's standard route instead, so the transaction still reaches the network. Arbitrum, Base, Arc, and Robinhood Chain don't broadcast transactions to a public mempool, so the standard route doesn't expose the transaction to front-running. This fallback differs from [MEV protection](/docs/mev-protection), which returns an error rather than using the public mempool.

Optimized submission applies to the node's existing HTTPS and WSS endpoints and to every [authentication method](/docs/authentication-methods-for-different-scenarios) of the node.

### Managing optimized submission

Optimized submission is on by default for a new node. When you deploy a node on Chainstack, optimized submission is already selected under **Add-ons** on the last step. To deploy without it, click **Disable** on the **Optimized submission** card. A node you create with the [Platform API](/reference/chainstack-platform-api-v2-create-node) gets optimized submission installed automatically.

The node's **Add-ons** tab shows whether optimized submission is on: its card shows **Active** with a **Disable** button when it is enabled, and **Enable** when it is not. The **Add-ons** tab is the only place that shows this status; no JSON-RPC method or Platform API field reports it.

To enable optimized submission on a node that doesn't have it, open your node on Chainstack, select the **Add-ons** tab, click **Enable** on the **Optimized submission** card, and complete the install. See [Install a node add-on](/docs/add-ons#install-a-node-add-on).

To use the standard node route, click **Disable** on the **Optimized submission** card. You can enable it again from the same tab.
