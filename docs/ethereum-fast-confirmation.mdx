**TLDR:**
* On Ethereum Hoodi [Global Nodes](/docs/global-elastic-node), the `safe` block tag follows the Fast Confirmation Rule (FCR) and typically trails `latest` by one or two blocks.
* `finalized` does not change: it still trails `latest` by about two epochs.
* Fast confirmation relies on network synchrony assumptions. Use `finalized` for actions you cannot reverse.
* On Ethereum Mainnet and Sepolia Global Nodes, `safe` keeps its standard meaning — the latest justified block.

## What the safe block tag returns with fast confirmation

With fast confirmation, `safe` returns the most recent block that the consensus client confirmed under the [Fast Confirmation Rule](https://github.com/ethereum/consensus-specs/blob/master/specs/phase0/fast-confirmation.md). The consensus client passes that block to the execution client as its safe block, so every method that accepts a block tag — [eth_getBlockByNumber](/reference/ethereum-getblockbynumber), [eth_call](/reference/ethereum-ethcall), [eth_getBalance](/reference/ethereum-getbalance), and the rest — resolves `safe` to it.

Under normal network conditions, the Fast Confirmation Rule confirms a block within one or two slots, 12 to 24 seconds. A skipped slot or a slot where the rule does not advance widens the gap by a few blocks until the next confirmation.

| Block tag | Without fast confirmation | With fast confirmation |
| --- | --- | --- |
| `latest` | Newest block | Newest block |
| `safe` | Latest justified block, typically 32 to 64 blocks behind `latest` | Latest fast-confirmed block, typically one or two blocks behind `latest` |
| `finalized` | Latest finalized block, typically 64 to 96 blocks behind `latest` | Unchanged |

## When the safe block tag lags or steps back

The Fast Confirmation Rule falls back to an older confirmed block when it cannot keep up, for example while the consensus client is syncing or after an error. During a fallback, `safe` can return an older block than the previous request, at worst the finalized block, and then moves forward again as confirmations resume.

Code that follows `safe` must not assume its block number grows by one block at a time. Handle a `safe` block number that stays the same, jumps forward by many blocks, or goes back.

## When to use finalized instead of safe

Use `finalized` when a reorganization past your confirmation point would cost money or cannot be undone. Finality comes from Ethereum's consensus and does not depend on network timing. Fast confirmation does.

* Use `finalized` to credit deposits, release bridge withdrawals, and settle payouts.
* Use `safe` with fast confirmation for confirmations shown in an interface, for indexers that already handle reorganizations, and for testing confirmation flows on Hoodi before you move them to Mainnet.

## Which Chainstack endpoints use fast confirmation

Fast confirmation is on for Ethereum Hoodi Global Nodes. Ethereum Mainnet and Sepolia Global Nodes return the standard justified block for `safe`.

To see which behavior an endpoint has, compare how far `safe` trails `latest`: one or two blocks means fast confirmation, and dozens of blocks means the justified block.

```javascript check-safe.mjs
import { ethers } from "ethers";

const provider = new ethers.JsonRpcProvider(process.env.CHAINSTACK_ENDPOINT);

const [latest, safe, finalized] = await Promise.all(
  ["latest", "safe", "finalized"].map((tag) => provider.getBlock(tag))
);

console.log(`latest:    ${latest.number}`);
console.log(`safe:      ${safe.number} (${latest.number - safe.number} blocks behind latest)`);
console.log(`finalized: ${finalized.number} (${latest.number - finalized.number} blocks behind latest)`);
```

Run the script with your Hoodi endpoint:

```shell
npm install ethers
CHAINSTACK_ENDPOINT=YOUR_CHAINSTACK_ENDPOINT node check-safe.mjs
```

On a Hoodi Global Node, the output is similar to the following:

```text
latest:    3999541
safe:      3999539 (2 blocks behind latest)
finalized: 3999458 (83 blocks behind latest)
```
