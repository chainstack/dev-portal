Optimism produces Subblocks, formerly called Flashblocks: partial blocks with pre-confirmed transactions, about every 200 ms. Optimism exposes them through the standard `pending` block tag, not through dedicated WebSocket subscriptions. To follow transactions in real time on Optimism, poll the `pending` block roughly every 200 ms and track the transactions that are new since the last poll. This guide does that with tested Python and JavaScript, then covers the pre-confirmed read methods.

<Info>
For how Subblocks work on Optimism, see [Subblocks on Optimism](/docs/flashblocks-on-optimism). For Base, which exposes Flashblocks as WebSocket subscriptions, see [Stream real-time transactions on Base with Flashblocks](/docs/base-streaming-transactions-flashblocks).
</Info>

## Prerequisites

* An Optimism mainnet HTTPS endpoint. On Chainstack, copy it from your Optimism node's **Access and credentials** tab — it looks like `https://optimism-mainnet.core.chainstack.com/<key>`. The examples use `YOUR_OPTIMISM_HTTPS_ENDPOINT` as a placeholder.
* Python 3.8+ with the `requests` library (`pip install requests`), or Node.js 18+ (the `fetch` API is built in, so there are no dependencies to install).

## Why Optimism uses the pending tag, not eth_subscribe

On Optimism, the Flashblocks subscriptions that exist on Base — `eth_subscribe("newFlashblockTransactions")`, `newFlashblocks`, and `pendingLogs` — are not exposed; calling them returns `-32602 Invalid params`. Like every OP Stack chain, Optimism has no public mempool (see [Mempool configurations](/docs/mempool-configuration)), so `eth_subscribe("newPendingTransactions")` reports only transaction hashes as the sequencer includes them in subblocks. The `pending` block tag gives you the transactions themselves and the pre-confirmed state, and it reflects the latest subblock and advances every ~200 ms.

## Track pre-confirmed transactions

Poll `eth_getBlockByNumber("pending", false)` every 200 ms and emit transaction hashes you have not seen before. Each poll returns the block the sequencer is currently building; within one block number the transaction list grows every ~200 ms as new subblocks arrive.

<CodeGroup>
```python Python
import time

import requests

HTTP = "YOUR_OPTIMISM_HTTPS_ENDPOINT"  # https://optimism-mainnet.core.chainstack.com/<key>


def rpc(method, params):
    response = requests.post(
        HTTP,
        json={"jsonrpc": "2.0", "id": 1, "method": method, "params": params},
        timeout=20,
    )
    return response.json()["result"]


seen = set()
while True:
    block = rpc("eth_getBlockByNumber", ["pending", False])  # False -> transactions are hashes
    for tx_hash in block["transactions"]:
        if tx_hash not in seen:
            seen.add(tx_hash)
            print(tx_hash)
    time.sleep(0.2)
```

```javascript JavaScript
// Node.js 18+ has a built-in fetch — no dependencies required.
const HTTP = "YOUR_OPTIMISM_HTTPS_ENDPOINT"; // https://optimism-mainnet.core.chainstack.com/<key>

async function rpc(method, params) {
  const response = await fetch(HTTP, {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ jsonrpc: "2.0", id: 1, method, params }),
  });
  return (await response.json()).result;
}

const seen = new Set();
while (true) {
  const block = await rpc("eth_getBlockByNumber", ["pending", false]);
  for (const txHash of block.transactions) {
    if (!seen.has(txHash)) {
      seen.add(txHash);
      console.log(txHash);
    }
  }
  await new Promise((resolve) => setTimeout(resolve, 200));
}
```
</CodeGroup>

You get a continuous flow of newly pre-confirmed transaction hashes:

```text
0xaf2b57f8c6b2b0d4b52d9c8d3b5d90e92170edcb1bb90b79eefd9327f12272b1
0xc63e87a5a7b79d1e7dd17bcbaacebc9f7ddbe463dce512374160970714602c2b
0x06ddb3029829356ca6aed0a7c85b5b7c1bde50c1110d727eeb84c24f86bbe259
```

The `seen` set de-duplicates hashes that repeat across polls of the same in-progress block. In a 30-second test against Optimism Mainnet, the script emitted 230 transaction hashes, about 8 per second.

## How the pending block evolves

Each poll of the `pending` tag returns the same block number with more transactions and a different pre-confirmation hash, until the block seals and the number advances. Polled with a 200 ms pause between requests:

```text
#158861051 hash=0x015e2ef4bb2cebaeb45a01963984f21f1200ca7da85fbea5a7f948d0272deaeb txs=14
#158861051 hash=0x58bafaf684a9490a0fceb3cc6e7b390dcb16c8d39cf8129235d47567e62ffa97 txs=51
#158861052 hash=0x9380d911407cec3754d9c9f2ebc40912c2e5f35111cab8a36063040ccd3d97e1 txs=7
#158861052 hash=0x388bed3af1dbdd80b45bc717d268146c9b2fdcf72fda67f002f304d42d4174ac txs=9
#158861053 hash=0xb65c6556b88fd5bc8cf48cc87fe99f50a67e36d120360f1aae3562a96d89b672 txs=6
```

Unlike Base, where the streamed block carries a zero hash until it seals, Optimism's `pending` hash is non-zero and changes with each subblock. The `pending` hash is not the hash of the sealed block, and the `pending` block's `stateRoot` is all zeros. Track transactions by their own hash, not by the block hash.

## Read pre-confirmed state

The `pending` tag also serves request-response reads against pre-confirmed state, which updates about every 200 ms instead of every 2 s with each canonical block:

* `eth_getBlockByNumber`, `eth_call`, `eth_getBalance`, `eth_getTransactionCount`, `eth_getCode`, `eth_getStorageAt`, and `eth_estimateGas` with the `pending` tag.
* [`eth_getTransactionReceipt`](/reference/optimism-gettransactionreceipt) and [`eth_getTransactionByHash`](/reference/optimism-gettransactionbyhash) return the pre-confirmed receipt or transaction as soon as it lands in a subblock.
* [`eth_sendRawTransactionSync`](/reference/optimism-sendrawtransactionsync) submits a signed transaction and returns its pre-confirmed receipt in the same response.

```bash
curl -s -X POST YOUR_OPTIMISM_HTTPS_ENDPOINT \
  -H "Content-Type: application/json" \
  -d '{"jsonrpc":"2.0","id":1,"method":"eth_getTransactionReceipt","params":["0x<tx hash>"]}'
```

## Production considerations

* Pre-confirmations are not final. The sequencer can abandon or reorganize the block in progress until the 2-second canonical block seals, so for settlement confirm against `latest` or a finalized block.
* Poll at ~200 ms. That matches the subblock cadence; polling much faster mostly returns the same state.
* De-duplicate by transaction hash. The same transaction appears in every poll of the block it belongs to until that block seals.
* A poll that lands after a block seals misses the transactions added to that block since the previous poll. To capture every transaction, also read each sealed block with `eth_getBlockByNumber`.
* `newPendingTransactions` carries transaction hashes only. Optimism has no public mempool, so the subscription reports a transaction when the sequencer includes it in a subblock. For transaction details, receipts, and pre-confirmed state, use the `pending` tag.
