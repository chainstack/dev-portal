## What is a Global Node?

Global Node is a service providing a load-balanced node that routes requests to the closest available location for a specific protocol, based on the caller's location. This ensures efficient service access for users worldwide by routing requests in an optimized manner.

The main advantages of Global Nodes are the following:

* Enhanced load balancing — Global Nodes include a large load balancer that can switch nodes if one fails or falls behind the chain head, thus ensuring uninterrupted service.
* Reduced latency — by distributing traffic to the nearest endpoint, Global Node reduces latency, leading to faster transactions and improved user experience.
* Global reach — Global Nodes can be accessed by anyone from any location in the world. They direct users to the endpoints nearest to their location, which maximizes the availability and responsiveness of services.
* High availability — Global Nodes are designed for high availability, ensuring that your DApp continues to run with minimal interruptions.
* Instant deployment — unlike regional Trader Nodes, which take 3-6 minutes to deploy, Global Node is ready in under a second.

<Note>
Global Nodes support [Warp transactions](/docs/warp-transactions) for high-speed transaction propagation on Ethereum, Solana, and BNB Smart Chain networks.
</Note>

## Trader Node deprecation and migration

Trader Nodes are deprecated and will be shut down on December 1, 2026. To ensure uninterrupted service, migrate your Trader Nodes to Global Nodes before that date.

Global Nodes replace the key Trader Node capabilities while adding more functionality:

* Per-network host — Global Nodes use a streamlined, network-specific hosting format.
* New auth token — you use a new authentication token associated with each Global Node deployment.
* Routing and modes — Global Nodes add routing improvements and flexible operating modes.
* Request units — request usage is standardized and measured consistently.
* Add-ons — access advanced features such as Warp transactions.
* Access rules — configure endpoint security with finer-grained controls.

## How to find your Trader Nodes

Before migrating, identify your active Trader Nodes. You can find them by checking the following:

* Host pattern — look for hosts containing `nd-...p2pify.com`.
* Platform API v1 — check for `type=shared` combined with `provider=chainstack_managed` or `vzo`.
* MCP `node_tier` — inspect nodes labeled under the Trader tier.
* Node usage traffic — review traffic patterns in the dashboard's Node usage section.

<Note>
Provider alone is not enough to identify a Trader Node, because Dedicated Nodes can run on the same providers. Also, Platform API v2 does not return the node type.
</Note>

## Reuse or deploy a Global Node

You only need one Global Node per network.

Before you delete a Trader Node, check whether you already have an active Global Node for the same network. If you do, reuse it. If not, deploy a new Global Node before or while migrating traffic.

## Plan node limits and migration strategy

Your subscription plan counts Trader Nodes as part of your total node capacity.

To avoid hitting your plan limit during migration, move one network at a time. Keep one free slot available so you can provision the new Global Node before deleting the old Trader Node.

## Endpoint URLs per protocol

Global Node URL structures vary slightly by protocol. Pay special attention to where the authentication token is placed:

* Avalanche — the auth token goes after the chain path, for example `/ext/bc/C/rpc/<token>`. The old Trader Node format (`/<token>/ext/bc/C/rpc`) returns a 404 error on Global Nodes.
* Aptos — the auth token goes before `/v1`.
* Beacon Chain API — the structure is `/beacon/<token>`.
* Basic auth — supported for HTTPS requests (returns 200) and WSS handshakes (returns 101).

## Add-ons and special configurations

### Warp transactions

Global Nodes support Warp transactions for Ethereum, BNB Smart Chain, and Solana Mainnet. These features may require a paid plan and additional usage eligibility.

### MEV protection

Warp transactions are mutually exclusive with MEV protection and optimized submission. Disable MEV protection on Ethereum and BNB Smart Chain before enabling Warp transactions.

## Agent runbook for Chainstack MCP Server

If you use the Chainstack MCP server to automate infrastructure tasks, follow the runbook pattern similar to `migrate-to-chainstack-with-ai`.

The runbook commonly uses:

* `list_nodes` with `node_tier`
* `get_deployment_options`
* `create_node`
* `get_node`
* `delete_node`
* `list_projects`

<Note>
The MCP server currently labels some Dedicated Nodes on `chainstack_managed` and `vzo` as Trader, because it relies on the `node_tier` field. A fix is in progress. Merge this change only after the MCP server fix is live.
</Note>
